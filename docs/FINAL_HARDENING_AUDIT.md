## Integridad financiera y agenda

Se mantienen ledger separado de ventas/cobros/gastos/comisiones, bigint en PostgreSQL, snapshots inmutables, compensaciones, fees originales no supuestos reembolsados y locks por tenant. Las pruebas existentes cubren split exacto/rollback, sobrepago, post concurrente, reglas versionadas y cambio concurrente de regla, avance/ajuste no aplicado dos veces, cierre único y reversal. Se agregan refund concurrente, dos liquidaciones simultáneas reservando una sola comisión, pago de liquidación concurrente, reintentos antiguos, import concurrente y fallo intermedio sin movimientos parciales. No se editó historia financiera real.

Agenda conserva GiST por staff e intervalos server-side, dos/tres staff simultáneos, mismo staff entre sucursales, disponibilidad diaria, descansos/cierres/time-off, conflicto al reducir turnos, duración 120, composición propia de servicios, cancelación/reprogramación/no-show/rebooking/walk-in. Se mantienen negativos de rulos y query params maliciosos por gateway real/RPC. [WEBSITE_INTEGRATION](WEBSITE_INTEGRATION.md) define el contrato; las pruebas browser de fixtures no equivalen a probar la landing externa publicada de 17:17. Reservas cloud siguen deshabilitadas.

El reparto es una **estimación**, no una deuda aprobada ni un pago. No descuenta automáticamente alquiler impago sin registrar, retiros o pérdidas anteriores. Salarios sí integran gasto operativo; la moneda es PYG entera y el resto se conserva. El período es el rango seleccionado de una sucursal; no existe consolidación societaria pagada. [Diseño de extensión mínima](PARTNER_DISTRIBUTIONS_DESIGN.md) documenta decisiones de negocio pendientes, snapshots aprobados, pagos/contramovimientos, saldos, retiros aplicados y pruebas requeridas.

## Operación, rendimiento y límites de evidencia

Outbox y jobs se confirman con la transacción de negocio. Claim usa SKIP LOCKED, lease, token nuevo, intentos acotados y backoff; el scheduler nativo tiene lock global de ejecución. Un proveedor faltante queda awaiting_configuration. Los tests ahora verifican falla/reclaim/dead y ejecución simultánea; no se inventa prueba de entrega a un proveedor que no existe. Auditoría, eventos y claves financieras no tienen una purga nueva. Falta política aprobada de retención y alertas con recepción comprobada. [Incidentes](OPERATIONAL_INCIDENTS.md) describe diagnóstico y recuperación.

`npm run test:load` mide 10/50/100 organizaciones, 2 sucursales y 5 staff por organización; 100 muestras por carga, 10 concurrentes por carga. [Resultados](verification/load-results.json) registra p50/p95/p99 y hardware. Incluye escenario concentrado y dashboard largo en la ejecución final. Es **SQL/RLS en PostgreSQL embedded**, con contención de máquina Windows de desarrollo, sin red/Data API/Auth HTTP/Realtime/Vercel. No acredita capacidad HTTP cloud. Las colas por tenant serializan dinero; medir espera de locks con tráfico real antes de fragmentar locks. Filtros, límites, cursores e índices existentes se conservan; ningún índice se borra por estar “unused” en una base vacía.

Hay límites conocidos: SSE puede abrir dos canales por pantalla de recepción y reconecta cada cuatro minutos; el catálogo de selección inicial carga 100 elementos y necesita validación UX con organizaciones grandes. El import usa transacción por batch y no sustituye reconciliación contable. El read-model staff histórico se identifica como tal. Los límites de payload y errores no certifican resistencia a DDoS. No se presenta una revisión estática como cobertura dinámica de todos los estados.
